- [x] Crash-recovery classification: a durable `SIGNING` claim becomes `OUTCOME_UNKNOWN`; a stuck `AUTHORIZATION_CONSUMED` becomes `FAILED_PRE_SIGN` (`AUTHORIZATION_LOST_BEFORE_SIGNING`), discarding the consumed authorization; other non-terminal jobs are preserved; nothing is auto-replayed; recovery is idempotent.

- [x] Strict internal contracts (`internal/api`): job/credential/authorize DTOs, a JSON decoder that rejects unknown fields and trailing content, and safe `/v1/health` readiness (`ready`, `database`) that exposes no credential inventory.

## Phase 2B — exact SoftHSM credential enrollment

- [x] Abstracted PKCS#11 behind a `token.Backend` interface so selection/proof are testable without hardware; the real cgo `github.com/miekg/pkcs11 v1.1.2` adapter lives behind `//go:build pkcs11` with a pure-Go stub for the default build. `CGO_ENABLED=0 go build ./...` stays pure-Go; `go build -tags pkcs11 ./...` compiles the adapter.
- [x] Exact, no-fallback selection (`token.Resolve`): the requested slot, certificate fingerprint, and CKA_ID must each match exactly one object; zero matches, multiple matches, an absent slot, or a moved/changed token serial all fail closed. There is no first-slot/first-cert/first-key fallback.
- [x] Module verification (`token.VerifyModule`): canonical symlink-free path, non-group/other-writable permissions, expected ownership, exact SHA-256 against the allowlist, and mode allowlist.
- [x] Certificate/private-key proof (`token.VerifyKeyMatch`): public-attribute cross-check without a PIN when the token exposes it, otherwise a single PIN-bearing RSA PKCS#1 v1.5/SHA-256 signature proof over a random nonce. RSA-only, matching the fixed policy.
- [x] Credential registry (`internal/credentials`): enrollment resolves + proves + persists the exact tuple; rejects duplicate certificates and out-of-validity certificates; derives a stable, opaque `physical_token_queue_key` from the token serial so multiple credentials on one physical token share a queue; enable/disable and `verify` re-probe; `remove` is refused while unreconciled (non-terminal) jobs reference the credential and preserves job evidence.
- [x] `yargi-signerctl` commands: `modules list`, `credentials probe|enroll|list|verify|disable|enable|remove`. The PIN is read only from a no-echo interactive TTY (rejected on a pipe/file), never via flag/env/file; output masks token serials and subjects unless `--local-details`; `remove` requires an interactive `yes` confirmation.
- [x] Safe `GET /v1/credentials` inventory returns only public metadata (full certificate fingerprint, masked subject `E*** A***`, issuer, serial suffix, validity, key type/bits, mode, status) and never module paths/digests, slot IDs, full token serials, labels, or CKA_ID.

## Phase 2C — durable job API, queue, events, and PIN challenge

- [x] `internal/pin`: signed ES256 challenge binding job/request IDs, input hash, certificate fingerprint, policy version, nonce, expiry, key ID, allowed JWE `alg`/`enc`, and the ephemeral recipient JWK + RFC 7638 thumbprint. The PIN envelope is a compact JWE restricted to the single ECDH-ES + A256GCM profile with a per-challenge ephemeral recipient key; decryption enforces the profile and the protected-header `kid` = challenge ID. Built on `github.com/go-jose/go-jose/v4 v4.1.4`.
- [x] Durable one-time consumption (`jobs.ConsumeChallenge`): a single transaction marks the challenge consumed and moves the job `PIN_REQUIRED → AUTHORIZATION_CONSUMED`; a repeat returns already-consumed and performs no second transition. No PIN or ciphertext column exists; the ephemeral private key is held in memory only.
- [x] `internal/signer` coordinator: enqueues jobs onto the token queue keyed **only** by `physical_token_queue_key`, reaches `PIN_REQUIRED`, issues the challenge, and blocks the token's queue slot until a decrypted PIN arrives via a bounded in-memory handoff — giving same-token serialization and cross-token parallelism. It hands the PIN to an injected `Operation` and never signs; the token login+sign Operation is Phase 2D.
- [x] Internal job endpoints wired to the coordinator: `POST /v1/jobs` (idempotent create + enqueue, `Idempotency-Key` must equal `command_id`), `GET /v1/commands/{id}`, `GET /v1/jobs/{id}`, `GET /v1/jobs/{id}/events?after=`, `GET /v1/jobs/{id}/pin-challenge`, `POST /v1/jobs/{id}/authorize`, `POST /v1/jobs/{id}/cancel`, with the safe error taxonomy and cancellation refused once authorization is consumed.

## Phase 2D — prepare, sign, finalize, verify, and artifact capabilities

- [x] `internal/artifacts`: in-process artifact store + just-in-time capability broker. Read capabilities are minted only after the broker verifies the artifact hash and size; write capabilities are bounded by a max size. Capabilities are one-use, method-scoped, artifact/job-scoped, and expiring; reuse, method mismatch, forged token, expiry, and size overflow all fail closed. Phase 3A replaces the transport without changing the contract.
- [x] `internal/planauth`: immutable `SigningPlan` with a canonical hash and a supervisor `PlanAuthorization` MAC-authenticated with a supervisor-only key. The supervisor validates the candidate plan against the immutable job manifest (job/command/version, input artifact/hash/size, certificate fingerprint, profile/algorithm/mechanism, policy) and an allowlisted format-engine version; it issues a one-use authorization bound to the plan hash and nonce. Verification is constant-time and consumes the nonce once; forged, replayed, expired, wrong-job, wrong-input, wrong-engine, and wrong-plan-hash authorizations all fail closed.
- [x] `internal/pades` wraps the quarantined eimza-go `SignBaselineBB`/`VerifyCryptographic` so API/worker code never imports `third_party` directly; the token participates only through the `crypto.Signer` seam.
- [x] Token-worker pipeline (`internal/signer` `TokenOperation`): resolve the exact credential, fetch the input through a read capability, rehash and re-verify hash/size, build the plan, obtain a supervisor `PlanAuthorization`, and sign. The `crypto.Signer` implementation consumes the authorization one-use and performs the durable `AUTHORIZATION_CONSUMED → SIGNING` compare-and-swap immediately before the single `C_Sign`, then finalizes, runs local verification, stores the output through a one-use write capability, records the output hash and normalized evidence, and terminates in `QUARANTINED`. A failure before the token call → `FAILED_PRE_SIGN`; an ambiguous token error → `OUTCOME_UNKNOWN`; a post-sign finalization/verification failure → `FAILED_POST_SIGN`; none ever re-sign.
- [x] `internal/validation`: `Local` structural/cryptographic verification and a digest-pinned, timeout-bounded `ExternalValidator` that fails closed on a digest mismatch or missing executable and normalizes outcomes to `valid | invalid | indeterminate`.

A fresh `upgrade head` builds the legacy schema then the signing subsystem; an already-populated legacy database is stamped at `0001` and upgraded to `0002` without touching existing rows. `env.py` runs synchronously against the app SQLite path with `foreign_keys=ON`.
- [x] Signing models + constraints (`app/models.py`, plan §9.1): `SigningArtifact`, `SigningCertificate`, `SigningCertificateAssignment`, `SigningRequest`, `SigningApproval`, `SigningDownloadAuthorization`, `SigningRequestEvent`, `SigningAuditEvent`, `SigningOutbox`, and `SigningCapabilityConsumption`. A partial unique index enforces one active owner per certificate; a per-request unique `(owner, operation, idempotency_key)`; a monotonic per-request event sequence; a manifest-immutability trigger fires once a request leaves the pre-queue states; append-only triggers protect the audit log against update/delete and request events against update. Owner foreign keys use `RESTRICT` so retained evidence cannot be cascade-deleted. No column stores a PIN, PIN ciphertext, password, or artifact capability.
- [x] Private streaming artifact store (`app/artifact_store.py`): bytes live only on a `0700` tree, never in SQLite. Writes stream to a `0600` temp file, hash while streaming, enforce a max-size cap, `fsync`, and atomically rename. Storage keys are opaque hex; every path is regex-validated and realpath-checked against the root, and reads use `O_NOFOLLOW`, defeating traversal and symlink escape.
- [x] Internal artifact broker + capability tokens (`app/artifact_capabilities.py`): HMAC-authenticated capabilities scoped to method + artifact + job + hash/size + nonce + expiry, minted just in time. The broker verifies the durable artifact binding, streams read/write, and records one-use consumption as a keyed one-way hash (`SigningCapabilityConsumption`); replay, expiry, method mismatch, forged token, output-already-written, and size overflow all fail closed. Capabilities are never logged or persisted raw.
- [x] Signer Unix-socket client + transport identity (`app/signing_client.py`): deadline-bounded `httpx` client over the private UDS; `SO_PEERCRED`/`LOCAL_PEERCRED` peer-credential capture with a UID allowlist and dedicated-group check; Ed25519 command authentication binding key id, method, canonical path/query, body SHA-256, timestamp, and nonce, with bounded skew, one-use nonce replay protection, and constant-time verification. Connect/transport failures surface as `SignerUnavailable`; safe signer errors as `SignerError`.
- [x] Orchestration (`app/signing_workflow.py`): deterministic command/job IDs; transactional outbox for `create_job`/`cancel` with an explicit guard that a PIN envelope can never be queued; dispatch with signer-unavailable retry/backoff and `409` reconciliation via `GET /v1/commands/{id}`; durable event projection that appends monotonic request events, ignores a stale cursor, and never invents a signer transition; and `GET /v1/credentials` certificate synchronisation that upserts only safe public metadata and marks vanished certificates unavailable (never deleted).
- [x] Local administration (`app/signing_admin.py`, plan §5.4): `sync-certificates`, `assign`, and `revoke-assignment`, enforcing one active owner per certificate (idempotent for the same owner, refused for a second) and auditing every mutation.
- [x] Safe audit writer (`app/signing_audit.py`): append-only rows with a forbidden-key guard that drops any secret-bearing field before it can reach the audit log.
- [x] Account behaviour (`app/api/account.py`): export now includes only safe signing metadata (no bytes, path, PIN, or capability); deletion refuses with `409` while retained completed evidence exists and otherwise purges the departing user's non-retained signing rows before removing the account.
- [x] Startup invariants + disabled mode (`app/main.py`, config): every signing flag is disabled by default and the startup check is then a clean no-op with no signer I/O; when enabled it refuses to start on missing capability secret, missing command key, or an unparseable pinned key and provisions the `0700` state directory. No `/api/signing` route is mounted yet (Phase 3B).

## Phase 3B — browser-facing signing routes and fresh authorization

- [x] All 14 `/api/signing` routes (`app/api/signing.py`, plan §8.1): `capabilities`, `challenge-keyset`, `certificates`, `POST/GET/DELETE artifacts`, `POST/GET requests`, `GET requests/{id}`, `confirm`, `events`, `pin-challenge`, `pin-envelope`, `cancel`, `download-authorization`, and `download`. The signer client, artifact store, and broker are injected as overridable dependencies so the FastAPI surface is fully testable without a live daemon.
- [x] CSRF, Origin/Host, and body/upload limits (`app/security.py`, `app/api/signing.py`): a double-submit `ya_csrf` cookie plus `X-CSRF-Token` header (constant-time compare) and exact Origin/Host (Referer fallback) guard every state-changing route; uploads are streamed to the private store with a byte cap, a `%PDF-` magic check, and a per-user upload rate limit; request models reject unknown fields so caller-supplied policy fields are refused.
- [x] Fresh authorization and one-use approvals: `confirm` and `download-authorization` require fresh account-password re-verification; the plaintext password is consumed by existing auth logic and never enters a signing record or audit payload; confirmation writes a one-use `SigningApproval` bound to request/input-hash/certificate-fingerprint/policy/expiry, reserves the output artifact, enqueues the immutable signer job through the outbox, and returns `202`.
- [x] Request idempotency: the `Idempotency-Key` header is required; the same key with identical input returns the original request, a different input returns `409`, and a missing key returns `400`.
- [x] Synchronous PIN-envelope relay (`pin-envelope`): reconciles durable signer state first, then relays the envelope synchronously with no logging, journaling, outbox entry, or audit of the envelope body; maps `consumed`/`already_consumed`, `delivery_unknown` (which sets a durable `pin_relay_status` marker that blocks any second envelope), `409`, `410`, `422`, and a `503` only when delivery is provably unreached. A test scans every signing table and confirms the envelope value appears nowhere.
- [x] Completed-output download: `download-authorization` issues a short-lived, one-use, output-SHA-256-bound authorization stored only as a one-way token hash; `download` streams the output only for the owner in `COMPLETED` under an unexpired unconsumed authorization whose output hash still matches, consumes it once, and sets `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, and a sanitized attachment filename.
- [x] Safe Turkish state/error copy (`app/signing_state.py`): a `STATE_LABELS_TR` map surfaces state copy to clients with no vendor, module, token, or PIN detail; route errors return safe Turkish `detail` text.
- [x] Disabled-feature behavior: with the feature off, `capabilities` reports `enabled:false` and every other signing route returns `404`.

## Phase 1A/1B gate — format conformance, two-validator matrix, fuzz, and trust outcomes

Advances the authoritative Phase 1 format/trust portion. It does **not** mark Phase 1 complete or lift quarantine: trust is indeterminate for the self-signed corpus and live SoftHSM (Phase 2B) is still pending.

- [x] Second independent full PAdES validator integrated: pyHanko 0.35.2 via a self-contained wrapper (`signing-service/tools/pades_validate_pyhanko.py`) that reports cryptographic integrity, byte-range coverage, and an explicit fail-closed trust/revocation outcome separately (`tools/requirements.txt` pins it).
- [x] Two-validator matrix (`internal/validation/matrix_test.go`): the eimza-go engine signs an accepted corpus fixture and both Poppler `pdfsig` 26.04.0 and pyHanko 0.35.2 accept the signature through the digest-pinned `ExternalValidator` seam (wrapper scripts `testdata/validators/{pdfsig,pyhanko}_validate.sh`); both reject a one-byte-tampered copy; the `MultiValidator` aggregate is fail-closed. Skips gracefully when a validator is absent, so it is opt-in evidence, never a false pass.
- [x] Fixed a real fail-open bug in `normalizeOutcome`: negative markers (`invalid`, `not valid`, `failed`, `no signature`) now win, so "Signature is Invalid" can never be read as valid.
- [x] Explicit fail-closed trust/revocation outcomes (`internal/validation/release.go`): `TrustOutcome.ReleaseAllowed()` permits release only when crypto, trust, and revocation are all `valid`. `TestTrustOutcomeFailsClosed` records the self-signed corpus as crypto-valid but trust/revocation indeterminate, so release is refused and output stays quarantined.
- [x] Versioned controlled PDF corpus (`internal/corpus`, `yargi-pdf-corpus-v1`): deterministically generated accepted classic-xref fixtures plus one fixture per rejected class (encrypted, existing-signature, AcroForm, prior-incremental, hybrid-reference, non-classic/xref-stream, malformed-xref, missing-header, non-catalog-root, oversized, empty). Digests are pinned in `testdata/pdf/manifest.json` and regression-checked; `pades.Sign` accepts every accepted fixture (round-trip verified) and fails closed on every rejected class.
- [x] Seeded Go fuzz targets over the parser and lexical scanners (`FuzzParse`, `FuzzContainsName`, `FuzzFindDictionaryEnd` in `third_party/eimza-go/pdf`) and preflight/verify (`FuzzVerifyLocal`, `FuzzSignPreflight` in `internal/pades`), each with a size bound and a no-panic / in-bounds invariant.
- [x] CI: added a fuzz smoke step and a step that installs poppler-utils + pyHanko and runs the two-validator matrix and trust-outcome tests; updated `docs/signing/INTEROPERABILITY_MATRIX.md` with the filled evidence.

## Phase 2E — daemon coordinator wiring and live SoftHSM end-to-end

Closes the "daemon coordinator wiring" and "live SoftHSM" blockers left deferred by Phase 2D. It does **not** lift quarantine or mark Phase 1 complete: the test certificate is self-signed, so trust stays indeterminate and every signed output remains `QUARANTINED`.

- [x] Shared wiring (`internal/assembly`): a single `Build(Deps) → Components` constructs the durable journal, credential registry, in-process broker, plan authorizer, token operation, PIN challenge signer, per-token queue, and coordinator. The daemon and the live end-to-end test call the same `Build`, so the test exercises the exact production wiring path.
- [x] Daemon wired (`cmd/yargi-signerd/main.go`): after journal recovery the daemon loads the allowlisted PKCS#11 module (`token.VerifyModule` → `token.NewBackend`), loads the ES256 challenge key (PEM P-256) and the supervisor HMAC key from disk, builds the pipeline, and calls `server.SetJobService`. It fails closed when an enabled token mode is missing the module alias, allowlist, or a key. The signer job endpoints (`POST /v1/jobs`, `pin-challenge`, `authorize`, …) are now served instead of returning `503`.
- [x] Config (`internal/config`): added `SIGNERD_MODULE_ALIAS`, `SIGNERD_CHALLENGE_KEY`(+`_ID`), `SIGNERD_SUPERVISOR_KEY`, and PIN-window/plan/authorization/capability TTLs, all with safe defaults; absolute-path validation for the new key paths; presence is enforced at daemon start, so the disabled default and existing config tests are unchanged.
- [x] Reproducible TEST-ONLY SoftHSM provisioning (`scripts/provision-softhsm-test-token.sh` + `cmd/yargi-softhsm-provision`, build tag `pkcs11`): initializes an isolated token, generates a self-signed RSA-2048 credential, and writes the private-key object `CKA_PRIVATE=false` (material stays `CKA_SENSITIVE`) plus the certificate via `C_CreateObject`, so the reviewed enrollment path can enumerate the key without login. The provisioning helper never touches the production signing path.
- [x] Live end-to-end test (`test/integration/live_softhsm_test.go`, build tag `pkcs11`, env-gated): enroll a real SoftHSM credential → create a job → reach `PIN_REQUIRED` → relay an ECDH-ES/A256GCM PIN envelope → single `C_Sign` → local PAdES verify → both independent validators (Poppler `pdfsig`, pyHanko) accept the signature and reject a tampered copy → job terminates `QUARANTINED` with no failure code. Skips gracefully without a provisioned token, so it is opt-in evidence, never a false pass.
- [x] CI: the signing-service workflow installs SoftHSM, provisions the token, and runs the live end-to-end test on Linux alongside the two-validator matrix.
- Known gap: real qualified tokens keep private-key objects `CKA_PRIVATE=true` (hidden pre-login); enrolling those needs a reviewed change to resolve keys via the public-key object or an authenticated enrollment session. Flagged, not silently changed.

## Phase 4 — React signing experience

Implements the browser-facing e-imza flow in the existing Vite + React SPA (`web/`) against the Phase 3B `/api/signing` routes. It changes no backend behaviour and stays inert until signing is enabled server-side.

- [x] Typed client (`web/src/lib/signing.ts`): every `/api/signing` route with same-origin credentials and the double-submit CSRF header read from the non-httponly `ya_csrf` cookie (seeded by the capabilities call) — capabilities, challenge-keyset, certificates, artifact upload/get/delete, request create/list/get, confirm, events, pin-challenge, pin-envelope, cancel, download-authorization, and one-use token download.
- [x] Browser PIN envelope (`web/src/lib/pinEnvelope.ts`), WebCrypto only, no JOSE dependency: verifies the ES256 challenge JWS against the pinned challenge keyset and the RFC 7638 recipient-key thumbprint, then encrypts the PIN as a compact ECDH-ES + A256GCM JWE with an ephemeral sender key and the challenge id bound in the protected `kid`. The PIN never leaves the browser except as ciphertext.
- [x] Signing view (`web/src/views/SigningView.tsx`): capability gating (disabled → informational card), certificate selection, PDF upload, request creation with a client `Idempotency-Key`, a fresh-password confirm dialog, live status polling with a Turkish state timeline, the in-browser PIN dialog, cancellation, and a fresh-password one-use download. Wired into the shell (sidebar nav, view router, `AppView`, header title, `pen` icon).
- [x] `tsc --noEmit` and `vite build` pass; `SigningView` is a lazy ~18 KB chunk.
- Not done here: live browser rendering against an enabled backend and the FastAPI↔daemon transport (the routes are disabled by default and the signerd bridge is unwired), so the deployed app performs no signing.

## Explicit non-claims

The current branch can produce a local software-key signature over a deliberately narrow test PDF corpus, solely for conformance development. Two independent PAdES validators now accept its cryptographic signature, but it does not access hardware, accept PINs from real users, or establish certificate trust/revocation/qualification — the corpus certificate is self-signed, so the trust outcome is indeterminate, release fails closed, and authoritative Phase 1 is not marked complete. Phase 3A/3B add the FastAPI control plane, system of record, and the complete browser-facing `/api/signing` route surface (ownership, CSRF/Origin, fresh-auth, immutable manifest, synchronous no-persistence PIN relay, and one-use hash-bound download), but every signing flag is disabled by default — so the deployed application performs no signing and its routes are feature-off unless explicitly enabled in a test environment. Phase 4 adds the React e-imza UI (capability gating, upload, confirm, in-browser ECDH-ES PIN envelope, status, download), but it too is inert while the feature is disabled and the FastAPI↔daemon transport is unwired. Phase 2E wires the daemon coordinator and demonstrates a live SoftHSM login→sign→two-validator flow end-to-end, but only against a self-signed test certificate, so every output stays `QUARANTINED` and is never a qualified signature. It must not be represented as production-ready, qualified, timestamped, LT/LTA-capable, or UYAP-integrated.
